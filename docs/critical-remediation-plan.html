🔴 P0-A: Production error messages are invisible to every user, on every action

This is almost certainly the direct cause of the crash screenshot.

Next.js redacts every uncaught throw inside a Server Action in production builds — the client never receives error.message, only a generic digest. Confirmed directly against the docs shipped with the installed Next.js version (not from memory):

node_modules/next/dist/docs/01-app/01-getting-started/10-error-handling.md

"For [expected] errors, avoid using try/catch blocks and throw errors. Instead, model expected errors as return values."

This codebase does the opposite everywhere — submitOrder, dispatchOrder, addLedgerEntry, rejectOrder, and every other server action use throw new Error('helpful message') paired with a client-side catch(err) { toast.error(err.message) }. This works fine in dev mode (real messages pass through) and silently breaks in production for every validation error on every role. A client can't see "PO image is required" or "Driver name is required" — they see exactly the banner in the screenshot, with zero actionable information.

Fix shape

  • Migrate server actions to the return-value error patterncritical
    Per Next's own recommended pattern: instead of throw new Error(msg), return { error: msg } (or a discriminated { success: false, error: msg } | { success: true, data } shape) from every server action that currently throws for expected/validation errors. Update every call site to check the returned shape instead of relying on try/catch. This touches every file in src/lib/actions/ — it's a mechanical but wide-reaching change, not a quick patch.
  • Add a global error boundary as a safety netcritical
    Add error.tsx boundaries at the /admin, /client, and root levels for the genuinely unexpected crashes (real bugs, not validation) that should still fail loudly — using error.digest to let you look up what happened server-side via logs, while showing the user something better than a blank red banner.

🟢 P0-B: Orders are priced using unit count instead of individual-bag count — 25–50x undercharge fixed

Found independently while tracing the crash. Code fix landed with regression tests; production audit completed — no historical undercharges exist.

The screenshot's own numbers prove it: 1,200 SB × ₱185 = ₱222,000. Per the domain spec (and the project's own dead-but-correct legacy pricing module), 1 SB = 50 individual 40kg bags, and price is per individual bag. Correct total: 1,200 × 50 × 185 = ₱11,100,000.

Live (broken) — src/components/orders/wizard/order-schema.ts
export function getSubtotalByBagType(jbQty, sbQty, jbPrice, sbPrice) {
  return jbQty * jbPrice + sbQty * sbPrice;   // treats unit count as bag count
}
export function getTotalIndividualBags(jbQty, sbQty) {
  return jbQty + sbQty;                        // same bug, used for split-delivery math too
}
Also broken — src/lib/actions/admin-helpers.ts (createOrderForClientPortal, admin-side manual orders)
totalAmount = params.jbQty * jbPrice + params.sbQty * sbPrice;   // identical bug
Correct formula already exists — dead code, src/lib/client-portal-data.ts (not imported anywhere)
export const BAG_EQUIVALENT = { JB: 25, SB: 50 };
export function getIndividualBagCount(jbQty, sbQty) {
  return jbQty * BAG_EQUIVALENT.JB + sbQty * BAG_EQUIVALENT.SB;   // this one's right
}

Fix status

  • Fix both live pricing formulas to use individual-bag countdone
    Landed. getSubtotalByBagType → (jbQty × 25 × jbPrice) + (sbQty × 50 × sbPrice); getTotalIndividualBags → jbQty × 25 + sbQty × 50; same fix in createOrderForClientPortal. The screenshot scenario is locked in as a regression test (1,200 SB @ ₱185 → ₱11,100,000) in order-schema.test.ts and admin-helpers.test.ts. The dead client-portal-data.ts reference module was deleted once the correct formula landed in live code.
  • Fix the split-delivery unit bug exposed by the pricing fixdone
    The wizard's split math divided jbQty units by total bags and subtracted units from bags (e.g. a 300-bag request on a 4 JB + 10 SB order recorded 2 JB + 10 SB = 550 bags). Resolved by pinning the denominations: deliver_now_qty/the wizard field are individual bags; deliver_now_jb/deliver_now_sb are whole units — matching what the resume-draft and redelivery code already assumed. New getSplitDeliveryUnits() helper does the bags→units conversion (proportional by bag-share, capped per type) and is used by the wizard's submit/draft paths and the client-actions fallback. approveOrder's split cap now compares units to units, and the split UI labels the field "individual bags". Regression tests cover the exact old failure.
  • Run the read-only audit against production datadone
    Done 2026-08-07: node scripts/audit-order-totals.mjs scanned production (4 orders) — none had order_items rows, so 0 auditable and 0 mismatches, ₱0 undercharge. The tool now falls back to the product's current price_per_bag if the order-time snapshot column is missing. As part of this, the missing migration 20260629_order_items_price_snapshot.sql (adds order_items.selling_price_per_bag) was applied to production — the app writes that column on order create, so new orders would otherwise have failed. Re-run the audit after real orders exist to confirm totals.
  • Decide and enforce the denomination of customer_balances.remaining_qtydone
    Decision: individual bags — matching the balance page's existing "individual bags" labels and the redelivery flow's ÷25/50 conversion. All writers now convert: approveOrder and dispatchOrder store remaining_qty/total_purchase as units × bag-equivalent, and dispatchOrder's redelivery deduction converts approved units back to bags. The redelivery boundary (submitRedeliveryRequest) converts the bag-denominated balance into units for order_items.requested_qty, so dispatch stock/profit math (which stays in units) is unaffected. The client balance summary and admin stock dashboard convert to consistent units. Existing rows are still in the old unit: run node scripts/wipe-customer-balances.mjs (dry-run by default; reconcile any pending balances with clients first) so every row going forward is created correctly.
