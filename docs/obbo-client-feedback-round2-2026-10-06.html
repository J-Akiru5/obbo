IssuesIssue-by-issue

Real · client issue 3

Balance still 100 after the redelivery was dispatched and completed

Fixed

DR-003 delivered the 100-bag balance and the order was marked completed, yet the balance row (order 1a0fb8cd, 100 JB, created by the original split dispatch) was still pending. Root cause: the clearing helper PATCHes updated_at — a column that does not exist on customer_balances — and writes remaining_qty = 0, which the table's original CHECK (remaining_qty > 0) rejects. PostgREST rejected the whole update; the caller only logged it, so the dispatch still reported success while the obligation survived.

Fixed with a migration (add updated_at, relax the check to >= 0), a hardened helper (list queries instead of maybeSingle(), explicit { updated, failed, errors } reporting, fulfilled/0 write), and a manual-DR path that clears balances for any DR against an already-dispatched PO — with a pre-dispatch guard so a first dispatch can't clear the balance it is creating.

Real · client issue 1

Batch dropdown overflowing the Dispatch Order modal

Fixed

The trigger rendered a full single-line sentence (VESSEL 1 — Available: … · Needed: …). The shared SelectValue was a flex flex-1 child with no min-w-0, so it refused to shrink, and the trigger's line-clamp-1 was neutralised by its own display: flex — the text simply painted past the container.

Fixed at both levels: the shared value/trigger now clip and ellipsize (min-w-0 overflow-hidden text-ellipsis), the trigger label is just the batch name (+ INSUFFICIENT when relevant), and the full Available/Needed detail moved into a wrapping summary card under the select plus the popup options. Modal widened to 560 px.

False positive · client issue 2

“SB remaining should be 343,750, not 343,550”

No code change

The client's expected value was computed from a starting balance of 344,950 SB. The actual stored starting balance was 344,750 SB, so exactly one 1,200-bag dispatch produces 343,550 — which is what the system recorded (verified from the activity log and ledger, with no manual stock adjustments in the log). The submitted screenshot is also from an earlier session: its redelivery modal shows a 2 SB dispatch, while this run's redelivery was 4 JB. Per your decision, stock is left as-is and the audit above is the client-facing answer.

Consistency check that settles it

Total JB deducted across the run = 1,100 (DR-002) + 100 (DR-003) = exactly 1,200 bags for a 1,200-bag JB order. Total SB deducted = exactly 1,200 bags for a 1,200-bag SB order. Both remaining values are arithmetically forced by those movements.
