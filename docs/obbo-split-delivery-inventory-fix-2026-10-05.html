Split Delivery Accounting, Inventory Units, Report Sync & Dispatch UI Fixes

Five client-reported discrepancies traced to a single root pattern: order quantities are stored in JB/SB units, while shipment stock, customer balances and warehouse reports are denominated in individual bags. Every boundary that mixed the two was fixed, redelivery dispatches now claim their share of the original prepaid PO, completed obligations clear automatically, and the dispatch batch dropdown no longer overflows its modal.

Deployment prerequisite — run the SQL migration

The atomic dispatch function dispatch_order_v2 is updated by a new migration. Until supabase/migrations/20261005_dispatch_order_v2_bag_stock.sql is executed in the Supabase SQL editor, the DB will still deduct raw units on dispatch even though the UI and ledger code are fixed. The migration is idempotent (create or replace) and safe to re-run.

Root causeThe denomination mismatch

OBBO sells cement in two container types — Jumbo Bags (JB) and Sling Bags (SB) — but bills per individual 40 kg bag. The data model stores both, and the two must be converted at every boundary: orders and ledger movements speak units; shipment stock, customer balances and warehouse reports speak individual bags. The client's live figures (200,000 JB bags / 345,000 SB bags) confirmed shipment stock is bag-denominated. Several code paths treated it as unit-denominated, which produced every downstream symptom: near-zero deductions, negative redelivery margins, and warehouse closing stock pinned at zero.

FixesIssue-by-issue

Client issue 1

Split delivery revenue & margins — re-dispatch produced negative profit

Fixed

A redelivery order is created with total_amount = 0 because the money was already recognized on the original prepaid PO. dispatchOrder prorated from that zero, so the re-dispatch was recorded with blank sales but was still charged the full landed + local cost per bag — a guaranteed negative margin. The original split dispatch also only recognized its proportional slice (₱203,500 of ₱222,000), so the PO never summed to its sale value.

Fix: when dispatching a redelivery order, resolve the original order by linked_po_number (excluding redelivery rows — see issue 4) and prorate its total_amount across this dispatch's bag-value share. Every split slice now claims exactly its portion; the two dispatches sum to the full PO.

After

Client issue 2

Inventory deduction subtracted units, not individual bags

Fixed

The atomic RPC dispatch_order_v2 deducted p_jb_qty / p_sb_qty (order units) directly from bag-denominated shipment stock. Manual ledger entries and DR edits had the same defect, and restockable returns credited bags after flooring them through a unit conversion that no longer applied. The result: 48 JB dispatched deducted 48 bags instead of 1,200.

Fix: a new migration replaces dispatch_order_v2 so validation and deduction use p_jb_qty × 25 / p_sb_qty × 50; ledger-actions, delivery-receipt-actions and dashboard-actions apply the same conversion on every stock read/write, and returns are credited as the exact individual-bag count.

Client issue 3

Physical Warehouse Inventory closing stock stayed at 0

Fixed

The closing-stock formula existed but had two failures: dispatched totals were read from ledger rows in units while every other term (received, returns, waste, prior closing) was in bags; and when no previous day's report existed, “yesterday's closing” started at 0, so the chain never left zero. The admin Reports page also hid the card behind a “not yet available” gate whenever today's report wasn't submitted yet.

Fix: dispatched totals convert units → bags; for today, when no prior report exists, the opening position is derived from live stock rolled back by today's net movements (opening = live − received + dispatched − returns + waste) so the computed closing resolves to the actual current stock. The admin card now renders the full formula — yesterday's closing, received, dispatched, returns, waste, and a dynamically computed Today's Closing — in individual bags for both JB and SB.

Client issue 4

Completed re-deliveries persisted in the obligation report & portal ledger

Fixed

The balance-clearing block looked up the original order with .eq('po_number', linked_po_number).maybeSingle() — but the original order and every redelivery order created against it share the same PO number. PostgREST returns a multiple-rows error for maybeSingle(), the code ignored the error, and the balance update never ran. The row stayed pending forever, so it kept showing in the Customer Obligation Report and the Client Portal Balance Ledger.

Fix: a shared applyRedeliveryToCustomerBalances() helper resolves the original order with order_type ≠ redelivery plus an explicit id ≠ exclusion, converts dispatched units to bags, decrements remaining_qty, and flips fully-covered rows to fulfilled (0 bags). It is invoked from both dispatch entry points — the fulfillment modal action and manual DR creation. The split-balance creation loop is also skipped for redeliveries so the same withheld bags can't be double-counted.

Client issue 5

Dispatch batch dropdown overflowed the modal

Fixed

The “Select Shipment Batch (Source of Truth)” select rendered a long single-line label (BATCH — Avail: … · Need: …) inside a w-fit trigger; the popup inherits the anchor width, so the whole control pushed past the modal container on long batch names and large numbers.

Fix: the trigger is constrained to w-full min-w-0 (truncating cleanly), the popup is capped at the viewport, and each option wraps instead of overflowing (whitespace-normal break-words) with a title tooltip. The label itself was simplified and made bag-aware: Available: N bags JB / N bags SB · Needed: N bags · INSUFFICIENT STOCK.

Related hardening

Collateral fixes found while tracing the five reports

  • PO clobbering stopped: redelivery dispatches no longer re-upsert the shared PO row — previously they overwrote the original PO's jb/sb and payment amounts with the re-dispatched slice and ₱0.
  • Return stock hint removed: the tracking UI warned that sub-unit bag returns “won't be restocked”; returns now credit the exact bag count, so the warning is gone.
  • Ledger dialog “Total Bags (auto)” now computes JB×25 + SB×50 instead of summing raw units.
  • Split-balance duplication guard: redelivery orders skip the split-balance creation loop (the original balance already tracks the remainder).
  • Labels corrected in Shipment Batches (“JB bags / SB bags”) and stock override dialogs.

Overlap note for reviewers

Two unmerged branches touch neighbouring surfaces: fix/split-delivery-amount-display (order-card display wording, already pushed) and staging/dispatch-modal-redesign (full dispatch-modal layout rework). This branch deliberately does not redo those changes; the dropdown-overflow fix here is scoped and may be superseded by the redesign when that branch merges.

Historical report limitation

The live-stock fallback for closing stock is applied only when the selected date is today. Past dates without a submitted daily report still cannot be reconstructed reliably (live stock includes later movements); the report leaves opening at 0 for those cases rather than fabricating a number. Daily submissions from here on rebuild the chain correctly.
