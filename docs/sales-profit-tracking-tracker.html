  • T-1: Editing a ledger entry silently corrupts its profit numbers critical ✅ Fixed & tested this session
    updateLedgerEntry() writes whatever jb, sb, or amount changes an admin makes directly to shipment_ledger — but never recomputes total_sales, gross_profit, net_profit, or selling_price_per_bag. Its updates type doesn't even include those fields. This is fully reachable: the "Edit" action on an existing ledger row in Inventory → Shipments tab lets an admin change quantity and amount, and the dialog wires straight into this function. After such an edit, the row is internally inconsistent (e.g. jb changes from 8 → 10, but total_sales/profit still reflect 8) — and every dashboard/report that sums these columns silently carries the stale number forward.
    src/lib/actions/ledger-actions.ts:98-179 (fn updateLedgerEntry) · src/app/admin/inventory/components/shipments-tab.tsx:247 (call site) · src/app/admin/inventory/components/ledger-entry-dialog.tsx (edit UI)
    Implemented: updateLedgerEntry now fetches the row's own current stored rates and recomputes total_sales/gross_profit/net_profit/selling_price_per_bag whenever jb, sb, amount, bags_returned, return_reason, or dr_number change — using that row's own historic landed_cost_per_bag/local_expenses_per_bag, never a fresh getCostConfig() call, preserving historical immutability. Folded in the Q1 decision at the same time: addLedgerEntry now gives return/waste/damage events real profit deltas instead of leaving them at zero, computed against the original dispatch row's stored rates (restockable returns reverse cost too; waste/damage don't, since that cost was already sunk). The duplicated dispatch-formula math in orders-actions.ts (T-5) was folded into one shared helper as part of this change.

    Verified: 5 new tests in ledger-actions.test.ts (dispatch formula, restockable-return delta, waste-return delta, the T-1 regression itself, and a no-op check for unrelated-field edits) — all passing alongside the existing 24. Clean tsc --noEmit and eslint on every touched file.

    Delivery note: I don't have push access to the actual GitHub repo (this was an anonymous read-only clone) — the change is included as t1-q1-ledger-profit-fix.patch alongside this tracker. Apply with git apply t1-q1-ledger-profit-fix.patch from the repo root, or copy the two changed files (admin-helpers.ts, ledger-actions.ts, orders-actions.ts) and the new test file in by hand.
  • T-2: Order line items record the wrong per-bag price high
    The order total is correctly computed from the source-dependent price (price_port vs price_warehouse, per the client's Port/Warehouse selection) — but order_items.selling_price_per_bag is recorded from the flat price_per_bag field instead, in both order-creation paths. Line items won't reconcile against the order total whenever the two prices differ, which is the normal case (₱210 vs ₱185 by default).
    src/lib/actions/admin-helpers.ts:172-193 (createOrderForClientPortal — used by admin manual PO + DR-triggered order creation)
    src/lib/actions/client-actions.ts:216-230 (submitOrder — the primary client order-wizard path)
    Fix shape: in both places, look up the price the same way totalAmount already does (source-aware: price_port for Port, price_warehouse for Warehouse, falling back to price_per_bag), and use that per-item value for selling_price_per_bag instead of the flat field.
  • T-3: Most of the Zod validation the CHANGELOG claims exists... doesn't high
    CHANGELOG.md (v1.0.0) states: "Added Zod validation schemas for all server action inputs (16 schemas across 15 domain files)." In the actual code, schemas.ts does define 16 schemas — but only 3 are ever imported and called (deliveryReceiptCreateSchema, deliveryReceiptUpdateSchema, purchaseOrderUpdateSchema). The other 13 — including ledgerEntryCreateSchema, ledgerEntryUpdateSchema, and costConfigSchema, all directly in this module's blast radius — are dead code that nothing ever calls .parse() or .safeParse() on. Worse: submitOrder() — the client-facing action that actually creates money-bearing orders — has no schema at all, not even an unused one.
    src/lib/actions/schemas.ts (16 schemas defined) · src/lib/actions/ledger-actions.ts, settings-actions.ts, products-actions.ts, shipments-actions.ts, orders-actions.ts, client-actions.ts (schemas never imported)
    Fix shape: wire the existing unused schemas into their matching functions (low effort — they're already written and shaped correctly) starting with ledgerEntryCreateSchema/ledgerEntryUpdateSchema and costConfigSchema. Separately, write and wire a schema for submitOrder's input — this one doesn't exist yet and is the highest-value gap since it's the only client-role-reachable action in this list.
  • T-4: No server-side floor on cost config or product prices medium
    cost-configuration-tab.tsx blocks values ≤ 0 client-side, but saveCostConfig() / saveCostConfiguration() apply no server-side check — same for createProduct/updateProduct on price_per_bag/price_port/price_warehouse. A direct action call (bypassing the UI) could set a negative or zero cost/price with no complaint from the server.
    src/lib/actions/settings-actions.ts:24-32 (saveCostConfig) · src/lib/actions/products-actions.ts (createProduct/updateProduct)
    Fix shape: part of T-3 — wiring the already-written costConfigSchema covers most of this in one move; add an equivalent min-bound schema for product price fields.
  • T-5: Currency math uses JS floats + Math.round, not a decimal library medium
    grossProfit/netProfit/sellingPricePerBag are computed with plain JS number arithmetic and Math.round(x * 100) / 100, repeated near-identically in three places, even though the DB columns are Decimal(14,2)/Decimal(10,2). At 2-decimal precision and current volumes this probably isn't producing visible errors today, but it's the kind of thing that eventually does, silently, on the exact numbers this module exists to get right.
    src/lib/actions/ledger-actions.ts:40-58 · src/lib/actions/orders-actions.ts:255-283 (same formula, duplicated)
    Fix shape: extract the shared formula into one helper (it's currently copy-pasted across two files, which is also its own maintenance risk), backed by a decimal library.
  • T-6: Default cost config isn't seeded in the base schema medium
    The cost_config row in admin_settings is only inserted by the 20260603_sales_profit_tracking.sql migration, not in supabase/schema.sql itself. A fresh DB bootstrapped from the base schema alone won't have it. Not a crash risk — getCostConfig() silently falls back to a hardcoded JS default — but it's a silent gap consistent with the "32 SQL files, no fresh-install guarantee" issue already on record.
    supabase/schema.sql (no cost_config seed) vs supabase/migrations/20260603_sales_profit_tracking.sql:10-12
